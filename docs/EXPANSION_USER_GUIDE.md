# Moongchi NameFix 1.0 기능 사용 안내

## 최신 화면 사용법

처음 실행하면 **자소 분리 해결**이 열립니다. 가운데 영역에 파일·폴더를 놓거나 **파일 선택**·**폴더 선택**을 누르세요. 검사가 끝나면 변경할 이름을 확인한 뒤 **선택한 이름 합치기**를 누릅니다. 실제 변경 전 확인은 계속 필요합니다. 파일을 더 넣으려면 창 위쪽의 **추가**, 다시 검사하려면 그 옆의 새로 고침 버튼(⌘R)을 씁니다. 자소 분리 해결은 항상 글자를 합치므로 형식을 고를 필요가 없습니다.

글자 바꾸기·번호 붙이기 등은 **파일 이름 일괄 변경**에서 합니다. 파일을 넣고 왼쪽 **변경 규칙**의 **+ 규칙 추가**에서 방법을 고른 뒤 값을 입력합니다. 화면을 열면 **텍스트 바꾸기** 규칙이 펼쳐져 있어 바로 값을 입력할 수 있습니다. 규칙은 기본으로 보이는 일반 파일의 이름에만 적용되며, 폴더 이름과 숨김 항목은 **+ 규칙 추가 → 고급 → 대상 범위**에서 켰을 때만 바뀝니다. 규칙을 바꾸면 목록 위 맨 앞에 **업데이트 필요**가 표시되며, 이것을 눌러 목록에 반영합니다. 고급 패턴·파일 정보·글자 저장 형식·순서 지정·CSV 목록·묶음 파일·프리셋도 **+ 규칙 추가**의 ‘고급’에서 엽니다. 갱신하지 않은 상태에서는 이름 변경을 실행할 수 없습니다. 좁은 창에서는 규칙과 목록을 세로로 스크롤합니다.

**자소 분리 해결**로 돌아오면 고급 규칙은 적용되지 않습니다. 작업실 초안은 현재 실행 중에는 유지됩니다. 앱을 다시 열면 항상 자소 분리 해결 화면에서 시작합니다. 적용한 기본 규칙 조합은 재시작 후 복원하지만 미적용 초안은 별도 저장하지 않습니다. 모든 기능은 무료입니다.

아무것도 넣지 않았을 때는 왼쪽에 메뉴가 이름과 함께 보입니다: **자소 분리 해결**, **파일 이름 일괄 변경**, **폴더 자동 감시**(새 파일 후보 수집), **복사한 글자 변환**, **작업 기록**, **설정**, **도움말**. 파일·폴더를 넣으면 메뉴는 아이콘 줄로 줄고(포인터를 올리면 이름과 설명 표시) 그 옆에 추가한 항목이 트리로 나타납니다. 트리에서 폴더를 누르면 그 안의 항목만 볼 수 있고, 모두 제거하면 메뉴가 다시 펼쳐집니다. 결과를 CSV로 저장·다시 검사·추가는 창 위쪽 버튼에 있습니다. 창이 좁아지면 왼쪽 영역은 자동으로 숨습니다.

macOS 14+ / Apple Silicon 전용이다. 현재 source는 기존 build3 Release 후보 이후 UI·설정 보완이 추가됐으므로 build3를 현재 source의 출시 승인본으로 취급하지 않는다. 기존 앱 설정·Olive 기본 테마·네 테마·창 크기 복원·선택·검사·기록은 유지한다.

## 동시 변경과 복구 위치

macOS 파일 조정에 참여하는 프로그램과 실제 이동을 조율한다. 대기 중 취소 또는 15초 접근 대기 한도를 지원한다. 일반 파일도 검사 이후 크기·수정 시각이 달라지면 다시 검사해야 한다. 디렉터리는 하위 항목 변경에 따른 자체 수정 시각 변화를 이 조건에서 제외한다.

조정 기능을 사용하지 않는 외부 프로그램의 동시 교체를 원자적으로 막을 수는 없다. 각 이동 직전·직후 raw 이름과 identity를 확인하며, 불일치하면 후속 변경을 중단한다. 작업 기록의 복구 위치에서 **Finder에서 보기** 또는 경로 복사를 사용한다. 정체가 다른 항목은 자동 복원 대상에 넣지 않는다. 실행 중 같은 파일의 저장·이동을 피하는 것이 지원 조건이며 파일 내용의 외부 변경까지 방지한다고 보장하지 않는다.

## 기본 흐름

1. 파일/폴더를 창 어디에나 드롭하거나 추가한다.
2. 글자 저장 형식을 자소 분리 합치기(NFC), 글자 분리하기(NFD), 글자 형식 그대로 두기 중 선택한다. 겉모양이 같은 이름의 문자 칸은 실제 저장 문자의 차이를 설명한다.
3. **파일 이름 일괄 변경**에서 **+ 규칙 추가**로 규칙을 만들고 **미리보기 갱신**을 누른다. 이 단계는 검사 결과만 바꾼다.
4. 목록의 변경 후 이름·제외 이유·묶음 파일을 확인한다. 화면 검색/정렬은 순번을 바꾸지 않는다. 순번 순서는 규칙 편집기에서 별도로 지정한다.
5. 이름 바꾸기 버튼을 누르고 확인 시트에서 바뀌는 개수·제외 개수·항목별 이름을 확인한 뒤 실행한다. 원본 내용은 수정하지 않는다. 작업 기록에서 새로운 역계획을 확인하고 되돌릴 수 있다.

화면 용어: 메타데이터는 ‘파일 정보’, CSV 매핑은 ‘CSV 목록으로 이름 바꾸기’, 파일 쌍은 ‘묶음 파일’, 정규식은 ‘고급 패턴 바꾸기 (정규식)’으로 표시한다. 아래 절은 같은 기능을 기술 용어로 설명한다.

작업 중 취소하면 처리 중이던 항목까지 마친 뒤 멈춘다. swap·cycle·묶음 파일처럼 한 묶음으로 처리하는 작업은 묶음 도중 취소하면 작업 기록의 복구 확인이 필요할 수 있다.

규칙은 위에서 아래 순서다. Finder가 관리하는 `.DS_Store`와 `.localized`는 규칙으로 이름을 바꾸지 않고 순번도 쓰지 않는다. 와일드카드(`*`, `?`) 규칙의 바꿀 글자는 `$`를 포함해 글자 그대로 쓰인다. 위치/삭제 수는 emoji 가족 같은 한 grapheme을 하나로 센다. 기본은 마지막 확장자를 보존한다(`archive.tar.gz`의 본문은 `archive.tar`). 숨김 이름 `.hidden`은 확장자 없는 본문이다. 확장자 편집은 내용/파일 형식 변환이 아니다. ‘적용 조건’은 규칙별 확장자 일치 조건이다. 메타데이터에 값이 없으면 제외하며 사용자가 대체 텍스트를 지정했을 때만 사용한다.

## 제공 범위

모든 기능이 무료다. 유료 등급·구매·계정·광고가 없고 의도적인 속도/개수 제한도 없다.

- 자소 분리 합치기·분리하기, 글자 구성 설명, 복사한 글자 변환
- 텍스트 바꾸기·앞뒤에 붙이기·삽입·앞뒤 삭제/유지·공백 정리·대소문자·지정 이름·확장자, 번호 붙이기(폴더별/반복/주기 포함)와 순서 지정
- 패턴 바꾸기(정규식·와일드카드), 악센트 제거, 규칙별 확장자 조건
- 프리셋 저장/복제/수정/가져오기/내보내기, 예제
- CSV/TSV 목록으로 이름 바꾸기, 파일 정보(촬영 날짜 등), 묶음 파일, 폴더 자동 감시
- 결과를 CSV로 저장, CLI, 메뉴바, Finder 서비스, 로그인 시 실행, 완료 알림
- Preview, 충돌 검사, 확인, 되돌리기, 복구

스캔 200,000개, 규칙 1,024단계, 텍스트 4,096 UTF-16, CSV 32MB 등 방어 한계는 모든 사용자에게 같다. 다음 실행 때 자동 복원하는 마지막 규칙에는 기본 규칙 조합만 저장하며, 입력 파일 경로와 수동 순서 경로는 프리셋·감시 폴더 규칙에도 저장하지 않는다. 패턴·파일 정보 등을 포함한 규칙을 다시 쓰려면 프리셋으로 저장한다.

## CSV와 파일 쌍

CSV/TSV는 UTF-8만 읽고 BOM·따옴표·개행을 지원한다. 원본 열은 절대 경로, 상대 끝 경로 또는 파일 이름이다. 선택된 자료에서 정확히 한 항목과 일치해야 하며 중복/불일치/한 파일의 복수 매핑은 차단한다. 새 이름은 경로 없는 leaf다. 전체 CSV가 모호하면 일부만 실행하지 않는다. 잘못된 CSV 문법/열은 행 번호로 안내한다.

기본 결과 CSV는 수식으로 읽힐 수 있는 셀을 작은따옴표로 보호한다. 원문 CSV는 원래 문자열을 보존하며 스프레드시트에는 텍스트로 가져와야 한다. 원시 경로/이름 bytes는 base64 열에도 보존한다. 원문 CSV를 재가져올 때 source와 destination 열을 선택한다. 원본 목록 파일은 수정하지 않는다.

파일 쌍은 `jpg,raw,xmp`처럼 확장자를 지정한다. 같은 부모·동일 raw 본문 이름을 묶어 하나의 순번과 본문을 쓰고 각 확장자를 유지한다. CSV/본문 이외 규칙/개별 조건과 함께 적용하지 않는다. 그룹 일부 선택·오류·충돌은 전체 그룹을 제외한다. 확장자 목록에서 우선하는 항목의 메타데이터가 그룹의 기준이며 없는 값은 fallback 또는 제외한다. 파일 쌍은 RAW 내용 해석 기능이 아니다. 그룹 전체 성공을 원자적으로 보장하지 않으며 부분 실패는 기록에 남는다.

## 메타데이터

| 형식 | 필드 | 직접 생성한 fixture |
|---|---|---|
| 일반 파일/폴더 | 생성·수정 시각, byte 크기 | PASS |
| JPEG/TIFF/HEIC | EXIF 촬영 시각, 카메라 모델 | PASS |
| MP3/M4A | 제목, 아티스트, 앨범, 트랙 | PASS (M4A 트랙의 모든 vendor 변형은 별도) |
| MOV/MP4 | 생성 시각, 초 단위 길이 | PASS |
| PDF | PDF 정보의 제목, 작성자 | PASS; Spotlight 색인 불필요 |

이미지는 속성만, 미디어는 컨테이너 metadata만, PDF는 정보 사전만 읽는다. 모든 codec/vendor tag 또는 RAW 메타데이터를 지원한다는 뜻은 아니다. 읽기 규칙을 끄면 기본 scanner는 파일 내용을 읽지 않는다. 이미지 256MB, PDF 64MB, 미디어 4GB 읽기 제한과 미디어 loading 취소 타이머 3초를 둔다. 라이브러리 자체의 모든 CPU 작업을 강제 종료하는 별도 프로세스 보장은 아니다.

시간대는 IANA 이름(예: `Asia/Seoul`, `UTC`) 또는 `source`다. 원본 EXIF/영상 오프셋을 해석하고 선택한 출력 시간대로 표시한다. `source`는 기록된 원본 오프셋, 없으면 UTC다. 파일 생성/수정 시간 자체에는 원본 시간대 정보가 없으므로 source 선택 시 UTC다. 포맷 기본은 `yyyy-MM-dd`; `/` 등 이름에 사용할 수 없는 결과는 제외한다. 촬영 날짜 뒤 일반 순번을 추가해 같은 시간의 충돌을 피할 수 있다.

## 폴더 감시

사이드바의 폴더 감시에서 현재 규칙으로 폴더를 등록한다. 감시의 기본 등록 상태는 없음이며 실제 변경은 항상 검토/확인 후다. 하위 파일을 재귀 검사하고 감시 루트와 하위 폴더 이름은 바꾸지 않는다. FSEvents IgnoreSelf, 폴더별 대기 ID 병합, 250ms 쓰기 안정화, content version 재검증을 사용한다.

처리한 raw 경로의 SHA-256 키와 identity/size/mtime를 앱 소유 설정에 저장하여 재시작 후에도 같은 파일을 재제안하지 않는다. hash는 입력을 선택하는 대신 동일한 처리 상태를 건너뛰는 데만 사용한다. 새 유입은 기존 확인 plan에 들어가지 않는다. 규칙 갱신 시 baseline을 비워 전체를 재검토한다. 권한 만료/위치 변경 시 다시 선택하고, 오류 또는 overflow는 전체 재검사를 안내한다. 저장 오류/새 schema 원본은 보존한다. 처리 기록은 공통 200,000개 한계를 두며 저장 실패는 안내한다.

## CLI

개발 빌드 또는 패키지에 포함된 `namefix` executable은 `--help`에 기본 문법을 제공한다.

```sh
./namefix --prefix 'Project_' --number 1 --json /absolute/path
./namefix --nfd --execute /absolute/path
./namefix --undo TRANSACTION-UUID --execute
```

기본 dry-run, 실제 실행은 터미널에서 `RENAME` 입력이 필요하다. non-TTY 실행/무확인 force는 차단한다. 앱과 History 및 process lock을 공유한다. exit 0 성공/미리보기, 1 오류, 2 제외/부분 실패, 3 취소다. JSON 출력은 raw bytes base64를 포함한다. `--rules-json`으로 규칙 조합을, `--recipe`로 저장한 프리셋을 전달할 수 있다. 모든 규칙을 제한 없이 쓸 수 있다.

## 남은 조건

SOURCE_RACE는 마지막 source 확인과 rename 사이 비협조 외부 프로세스가 파일을 교체하는 경우다. no-replace는 덮어쓰기를 막지만 expected-inode를 원자 조건으로 받지 않아 다른 항목의 임시 rename까지 완전히 예방하지 못한다. post-check 중단과 증거 보존은 구현했으며 해결 완료로 표시하지 않는다.

별도 단계: 출시 QA·서명·공증·배포 준비.

새 journal event는 schema 2로 기록하고 기존 schema 1은 변경 없이 읽는다. schema 2를 모르는 이전 앱은 해당 기록을 유효하지 않다고 판단하므로 새 swap/group 기록을 구식 Undo로 해석하지 않는다. 새 기록의 Undo/Recovery에는 최신 확장 개발본을 사용한다.
