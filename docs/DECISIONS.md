# Moongchi NameFix 결정

### D-001 macOS 14+ Apple Silicon arm64 전용 [accepted]
- 날짜: 2026-10-04
- 결정: 현재 제품은 macOS 14 이상 Apple Silicon arm64만 지원한다. Intel/Windows/universal2는 현재 범위가 아니다.
- 이유: 현재 project.yml, 빌드·검증 환경과 사용자가 확정한 플랫폼 override를 일치시킨다.

### D-002 SwiftUI + AppKit와 기존 계층 경계 유지 [accepted]
- 날짜: 2026-10-03
- 결정: UI는 SwiftUI + AppKit, 순수 이름/규칙 모델은 NameFixCore, 실행 조정은 Application, 파일시스템·저장은 Infrastructure가 담당한다.
- 이유: 이미 구현·검증된 책임 경계를 유지하고 문서 정비를 이유로 리팩터링하지 않는다.

### D-003 APFS 안전 mutation과 source-race 한계 공개 [accepted]
- 날짜: 2026-10-04
- 결정: local writable APFS만 mutation 대상으로 삼고, no-replace·durable journal·NSFileCoordinator 협조·identity/raw/version 재검사·post-check·보존/Recovery를 사용한다. 비협조 외부 writer의 source 교체를 원자 예방한다고 주장하지 않는다.
- 이유: Darwin의 현재 사용 계약에는 expected-inode 조건부 atomic rename 보장이 없으며 실제 경합 fixture도 이 한계를 재현했다.

### D-004 Free/Pro capability는 구현하되 실제 공급자 미구성 시 fail-closed [superseded by D-014]
- 날짜: 2026-10-04
- 결정: Free 기본 이름 정리와 Pro 고급 반복 작업의 capability 경계를 코드에 유지한다. Unconfigured entitlement는 Pro를 허용하지 않으며 Debug 개발 스위치를 실제 구매로 취급하지 않는다.
- 이유: 기능 구현과 실제 판매/영수증 검증을 분리해 권한 우회를 막는다.

### D-005 기본 제품 경로에 AI/OCR/RAG를 넣지 않음 [accepted]
- 날짜: 2026-10-04
- 결정: Unicode 정규화와 현재 이름 변경 엔진은 결정론적 로컬 로직을 사용한다. AI/OCR/RAG는 승인되지 않은 향후 후보이며 현재 mutation 경로에 연결하지 않는다.
- 이유: 정확한 Unicode 처리에 생성 모델이 필요하지 않고, 내용 접근·모델 용량·지연·개인정보 계약을 새로 만들기 때문이다.

### D-006 간편 자소 분리 화면과 일괄 변경 작업실 분리 [accepted]
- 날짜: 2026-10-04
- 결정: 첫 화면은 자소 분리 해결 중심, 고급 규칙은 별도 이름 일괄 변경 작업실로 제공한다. native sidebar와 목적별 도구 메뉴, Olive 기본 + System/Dark/Light, ko/en/ja, 반응형 창을 유지한다.
- 이유: 기존 기능을 숨기지 않으면서 첫 사용 복잡도를 낮춘다.

### D-007 배포 채널은 아직 확정하지 않음 [superseded by D-023]
- 날짜: 2026-10-06
- 결정: 현재 source의 App Sandbox는 OFF이고 직접 배포용 Developer ID 흐름이 준비돼 있지만, 최종 판매/배포 채널을 직접 배포 또는 Mac App Store 중 하나로 아직 확정하지 않는다.
- 이유: App Store 선택은 sandbox/entitlement와 판매 공급자 설계에 영향을 주므로 Release Task에서 사용자 결정과 최신 공식 정책 확인이 필요하다.

### D-008 만능프롬프트 Reference는 Bootstrap 기준으로만 사용 [accepted]

### D-009 과거 문서 대신 Git 이력을 사용 [accepted]

### D-010 Windows→macOS handoff는 제품 공통 명세 전달에만 사용 [accepted]
- 날짜: 2026-10-06
- 결정: 현재 macOS 저장소는 Windows 개발 handoff 패키지나 Windows 개발 이력에 실행 의존하지 않는다. 번역은 Resources/Localizable.xcstrings, 폰트는 Resources/, 앱 아이콘은 assets/branding/NameFix-Original.png를 각각 단일 원본으로 사용한다.
- 이유: 동일 제품의 기능·사용자 흐름·안전 요구는 계승하되 Windows 구현/개발 산출물 전체를 macOS 프로젝트의 영구 입력으로 유지하면 중복 SSOT와 불필요한 저장소 비대화를 만든다. 향후 플랫폼 이식도 공통 Product/UI·UX 명세 + 대상 플랫폼 Native Spec 방식으로 한다.

### D-011 화면 문구는 일반 사용자 용어를 우선 [accepted]
- 날짜: 2026-10-06
- 결정: UI에는 NFC/NFD, 정규화, 메타데이터, 정규식 같은 기술 용어를 그대로 내세우지 않고 사용자 목적 중심 표현을 쓴다. 기술명이 꼭 필요하면 ‘쉬운 이름 · 기술명’ 또는 괄호로 덧붙인다. 기술적으로 의미가 달라지는 번역은 하지 않으며, 세부 표기 규칙은 DESIGN.md가 원본이다.
- 이유: 출시 전 리뷰에서 상태 표시·필터·도움말·확인 시트에 개발 용어가 노출돼 처음 쓰는 사용자가 별도 설명 없이 이해하기 어려웠다.

### D-012 사용자 취소는 처리 중인 항목을 마친 뒤 적용 [accepted]
- 날짜: 2026-10-06
- 결정: 단일 항목 이동에서 source → temporary가 끝난 뒤의 취소 요청은 해당 항목을 final까지 마치고 다음 항목 전에 멈춘다. swap/cycle/묶음 파일 그룹은 현재 동작(그룹 도중 취소 시 Recovery)을 유지한다.
- 이유: 화면은 “현재 항목을 마친 뒤 중지”라고 안내하지만 실제로는 취소 시점에 따라 항목이 숨은 임시 이름에 남아 복구가 필요했다. 안전 검사(no-replace, identity 확인, journal 순서)는 바꾸지 않는다.

### D-013 화면은 상태에 필요한 control만 보여 준다 [accepted]
- 날짜: 2026-10-06
- 결정: 입력이 없을 때는 빈 상태 하나가 유일한 입력 화면이며 결과용 control을 두지 않는다. sidebar는 부제 없는 한 줄 navigation, toolbar는 sidebar 접기만 둔다. 이름 일괄 변경은 일상 작업 선택을 먼저 보여 주고 규칙 편집 전체는 ‘고급 규칙’을 펼쳤을 때만 노출한다. 기능은 지우지 않고 처음 보이는 시점만 늦춘다. 세부 계약은 DESIGN.md가 원본이다.
- 이유: 사용자가 실제 화면에서 입력 UI 중복, 빈 상태의 결과용 control 노출, sidebar 부제, 일괄 변경 화면의 복잡함을 지적했다. 이전 화면 구조는 사용자가 승인한 적이 없다.

### D-014 모든 기능을 무료로 제공 [accepted]
- 날짜: 2026-10-06
- 결정: 유료 등급을 두지 않는다. 앱과 CLI는 항상 전체 access로 동작하고 화면·문구에서 Pro·구매 표시를 없앤다. 규칙 집합을 access 수준에 대해 검증하는 내부 구조와 그 test는 남겨 둔다. 다음 실행 때 자동 복원하는 ‘마지막 규칙’은 종전처럼 기본 규칙 조합만 대상이며, 패턴·파일 정보 등을 포함한 규칙은 프리셋으로 저장해 다시 쓴다.
- 이유: 사용자가 “Pro 없음, 무료로 모두 제공”을 지시했다. 구매 공급자·상품 구성·영수증 검증이 필요 없어져 출시 Gate가 줄고, 구매할 수 없는 Pro 표시가 화면에 남는 문제도 사라진다.

### D-015 sidebar는 아이콘 레일과 추가 항목 트리 [superseded by D-016]
- 날짜: 2026-10-06
- 결정: sidebar 왼쪽 끝에 아이콘만 있는 레일(tooltip 제공)로 화면·도구·작업 기록·설정·도움말을 두고, 그 옆 패널에는 추가한 파일·폴더의 트리를 보여 준다. 트리의 폴더를 누르면 목록이 그 안의 항목으로 좁혀진다. sidebar 접기 버튼은 없애고 title bar band에 앱 이름 NameFix를 표시한다. 좁은 창에서는 sidebar가 자동으로 숨는다.
- 이유: 사용자가 이 구조를 직접 제안했다. 트리가 ‘추가한 위치’ 목록과 폴더별 보기를 한곳에서 해결한다. 아이콘만으로는 처음 보는 사용자에게 뜻이 덜 분명할 수 있어 tooltip, 접근성 이름, 상단 band의 화면 제목으로 보완한다.

### D-016 왼쪽 영역은 입력 상태를 따르고, 즐겨찾기는 감시와 분리 [accepted]
- 날짜: 2026-10-06
- 결정: 입력이 없으면 펼친 navigation만 보이고 폴더 트리는 없다. 파일·폴더가 추가되면 navigation이 아이콘 레일로 줄고 그 옆에 폴더 트리가 나오며, 모든 입력을 제거하면 자동으로 되돌아간다. 사용자가 관리하는 toggle은 두지 않는다. 즐겨찾기는 빠른 접근 shortcut일 뿐 background 감시와 결합하지 않으며, 실시간 감시는 ‘폴더 자동 감시’에 명시적으로 등록한 폴더만 수행한다. 세부 계약은 DESIGN.md가 원본이다.
- 이유: 사용자가 ‘항상 레일 + 트리’ 구조(D-015)를 실제 화면에서 본 뒤, 입력이 없을 때는 이름이 보이는 메뉴가 필요하고 트리는 입력이 있을 때만 의미가 있다고 지시했다. 즐겨찾기가 감시를 암묵적으로 켜면 사용자가 모르는 background 동작이 생긴다.

### D-017 개수·진행 상황·알림은 하단 상태 표시줄 한 곳 [superseded by D-018]
- 날짜: 2026-10-06
- 결정: content 맨 아래에 항상 보이는 상태 표시줄을 두고 “전체 N개 중 M개 표시”, 진행 상황과 취소, 알림 문구를 모두 거기에 표시한다. 결과 목록 위에 끼어들던 진행 줄과 화면 아래에 떠오르던 알림 banner는 없앤다. primary 버튼과 필터 역할을 하는 요약은 옮기지 않는다.
- 이유: 사용자가 하단 상태바를 검토해 도움이 되면 채택하라고 지시했다. 검토 결과 진행 줄과 알림 banner가 나타날 때마다 표 위치와 높이가 달라지던 문제가 없어지고, 두 화면과 모든 상태에서 같은 자리에서 상태를 읽을 수 있어 채택했다. 긴 알림은 한 줄로 잘리므로 누르면 전체 문구를 보여 준다.

### D-018 개수·진행 상황·알림은 맨 아래 줄 왼쪽, primary 버튼과 같은 줄 [accepted]
- 날짜: 2026-10-06
- 결정: 별도의 상태 표시줄을 없애고, 거기 있던 개수·진행 상황(취소 포함)·알림을 pane 맨 아래 줄의 왼쪽에 둔다. 오른쪽에는 primary 버튼이 있다. 진행 상황과 알림을 목록 위에 끼워 넣지 않는다는 D-017의 원칙은 유지한다.
- 이유: 사용자가 상태 표시줄을 실제 화면에서 본 뒤 제거하고 버튼 왼쪽 빈자리에 표시하라고 지시했다. 아래쪽에 줄이 두 개 생기지 않고, 정보가 실행 버튼 바로 옆에 있어 시선 이동이 줄어든다.

### D-019 첫 실행 소개는 밝은 색 고정, ‘다시 보지 않기’ 전까지 실행 때마다 표시 [accepted]
- 날짜: 2026-10-06
- 결정: 앱을 열 때 4쪽짜리 소개 sheet를 보여 준다. 내용은 장점 소개에 한정하고, 앱 테마와 상관없이 밝은 색으로 그린다. ‘다시 보지 않기’를 켜고 닫아야 다음 실행부터 나오지 않으며, 설정과 도움말 메뉴에서 다시 열 수 있다.
- 이유: 사용자가 지시했다. 소개가 열려 있는 동안 OS에서 넘어온 파일은 대기했다가 닫으면 추가된다.

### D-020 앱은 항상 자소 분리 해결 화면에서 시작 [accepted]
- 날짜: 2026-10-06
- 결정: 종료할 때 어느 화면이었든 다음 실행은 자소 분리 해결 화면에서 시작한다. 파일 이름 일괄 변경에서 적용했던 규칙은 초안으로 남아 그 화면에 들어가면 다시 보인다.
- 이유: 사용자가 시작 화면의 기본을 자소 분리로 지시했다. 앱의 주 용도가 자소 분리 해결이고, 시작하자마자 지난 규칙이 걸린 일괄 변경 화면이 나오면 의도하지 않은 변경 목록을 먼저 보게 된다. 이전의 ‘마지막 화면 복원’ 동작을 대체한다.

### D-021 즐겨찾기 폴더를 v1.0에 포함 [accepted]
- 날짜: 2026-10-06
- 결정: 폴더를 즐겨찾기에 추가·제거할 수 있고, 즐겨찾기를 고르면 현재 입력에 추가해 그 시점에 검사한다. 로컬 설정에 경로와 bookmark를 저장한다. 등록만으로 감시를 시작하지 않으며(D-016의 정책 그대로) 폴더 자동 감시는 사용자가 명시적으로 등록한 폴더만 대상으로 한다. 열 수 없는 즐겨찾기는 조용히 넘어가지 않고 표시한 뒤 다시 선택하게 한다. 제거는 shortcut만 지운다. 별도 화면 없이 첫 화면의 왼쪽 메뉴와 추가 메뉴에 둔다. 최근 폴더는 ‘지나간 기록’(사용자가 기억을 켠 경우), 즐겨찾기는 ‘사용자가 고정한 것’으로 구분하고, 같은 폴더는 한 번만 나열한다.
- 이유: 사용자가 반복해서 쓰는 폴더에 빨리 접근하기 위한 편의 기능으로 v1.0 포함을 결정했다.

### D-022 일괄 변경의 기본 대상은 보이는 일반 파일 [accepted]
- 날짜: 2026-10-06

### D-027 이름을 바꾸는 범위는 로컬 writable APFS(내장·외장), 그 밖은 이유와 함께 그대로 둔다 [accepted]

### D-028 작업 기록에 volume UUID를 남기고 다시 연결한 volume을 UUID로 확인한다 [accepted]
- 날짜: 2026-10-07
- 결정: 계획한 작업마다 volume UUID를 기록한다(선택 필드, 예전 기록은 없음). Undo와 Recovery는 기록의 UUID와 지금 mount된 volume의 UUID가 같을 때만 device 번호를 현재 값으로 바꿔 identity를 확인하고, UUID가 다르면 번호가 같아도 기록을 쓰지 않는다. 파일 번호와 생성 시각은 계속 정확히 일치해야 한다.
- 이유: device 번호는 mount할 때마다 바뀔 수 있어, 외장 드라이브를 다시 연결하면 같은 파일인데도 Undo가 거부됐다. 반대로 번호가 재사용되면 다른 volume을 같은 것으로 볼 여지가 있었다. UUID는 volume 자체를 가리키므로 두 경우 모두 더 정확하다. identity 확인을 느슨하게 한 것이 아니라 device 번호보다 정확한 기준을 더한 것이다.

### D-031 이체자 한자(CJK 호환 한자)는 합치기·분리에서 그대로 둔다 [accepted]

### D-033 sandbox에서는 사용자가 허용한 폴더에서 walk를 시작한다 [accepted]
- 날짜: 2026-10-07
- 결정: 폴더를 여는 규칙을 AccessRoots 하나에 둔다. 직접 배포판은 지금처럼 "/"에서 시작해 모든 조상을 O_NOFOLLOW로 연다. sandbox에서는 조상을 열 수 없으므로 사용자가 허용한 폴더(AuthorizedRoot: raw 경로, 폴더 identity, volume UUID)의 FD에서 시작해 그 아래를 같은 방식으로 내려간다. 허용한 폴더 밖은 열지 않고 FolderAccessNeeded로 알린다. 허용한 폴더가 옮겨지거나 다른 폴더로 바뀌면 쓰지 않는다. - 이유: macOS가 허용한 범위가 신뢰의 기준점이 되고, 그 아래로 link를 따라가지 않는다는 성질은 그대로다. 직접 배포판의 검사는 줄이지 않는다.

### D-034 다시 실행한 뒤의 접근은 필요한 곳에만 bookmark로 남긴다 [accepted]
- 날짜: 2026-10-07
- 결정: security-scoped bookmark를 남기는 곳은 즐겨찾기, 감시 폴더, 사용자가 켠 최근 폴더, 그리고 끝난 작업을 되돌릴 수 있는 폴더(access.json)뿐이다. 마지막 것은 그 작업 기록이 지워질 때 함께 지운다. 한 번 열어 본 폴더는 남기지 않는다. bookmark가 연 폴더는 기록의 volume UUID와 폴더 identity가 같을 때만 쓰고, 다르면 버린다. 시스템이 stale이라고 한 bookmark는 폴더가 열리면 새로 만들어 바꾼다. 접근을 얻지 못하면 Undo를 실패로 추정하지 않고 그 폴더를 다시 고르게 한다. 작업 기록(journal) 형식은 바꾸지 않았고, 접근 정보는 별도 파일에 version을 달아 둔다.
- 이유: 스토어판에서 앱을 닫았다 열어도 되돌리기가 돼야 한다. 동시에 지속 권한은 이유가 분명한 곳에만 있어야 한다. bookmark만 같다고 다른 디스크를 믿지 않는다(D-028과 같은 원칙).

### D-035 스토어판에는 CLI를 넣지 않는다 [accepted]
- 날짜: 2026-10-07
- 결정: Mac App Store판은 GUI 앱만 담는다. 직접 배포판의 namefix CLI는 그대로 제공하고 기능을 줄이지 않는다.
- 이유: sandbox 안의 CLI는 사용자가 터미널에서 넘긴 경로에 접근할 수 없어 쓸모가 없고, 앱 번들 밖에 설치하는 흐름은 스토어 배포와 맞지 않는다. CLI가 필요한 사용자는 직접 배포판을 쓴다.

### D-036 작업 기록의 확정 수준을 사용자가 고른다 [accepted]
- 날짜: 2026-10-07
- 결정: 설정에 ‘이름을 더 빠르게 바꾸기’를 둔다. 기본은 꺼짐이며 지금까지와 같이 항목의 기록마다 F_FULLFSYNC로 확정한다. 켜면 항목 기록은 F_BARRIERFSYNC(순서 보장)로 쓰고, 작업의 첫 기록·실패 기록·마지막 기록은 그대로 F_FULLFSYNC로 확정한다. 내장 드라이브가 아닌 곳이 하나라도 있으면 설정과 무관하게 기본 방식을 쓴다. CLI는 기본 방식만 쓴다.
- 바뀌지 않는 것: 덮어쓰지 않는 rename, 이름 변경 전후의 identity·내용 version 확인, 충돌 검사, 기록의 형식과 순서, Undo·Recovery, volume 확인.
- 감수하는 것: 켠 상태에서 전원이 갑자기 끊기면 마지막 몇 항목의 기록이 디스크에 없을 수 있다. 그 항목은 이름이 바뀌었어도 작업 기록에 없어 Undo 대상이 아니다. 파일 내용은 어느 경우에도 바뀌지 않는다. 앱 강제 종료나 충돌에서는 차이가 없다.
- 이유: 사용자가 User QA에서 속도를 지적했고(1,000개 약 30초), 시간의 대부분이 기록 확정이었다(1회 약 5ms × 항목당 5회). 사용자가 안정성과 속도를 직접 고르게 하기로 했다. 측정(Debug, 같은 장비): 1,000개 이름 변경 약 31초 → 약 10초.
